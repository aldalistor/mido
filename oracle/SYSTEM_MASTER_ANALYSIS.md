# وثيقة التحليل الموحد لنظام أونكس

## 1. الهدف والنطاق

الهدف هو إعادة تكوين نظام محاسبي مؤسسي حديث انطلاقاً من نظام Oracle Forms قديم، مع الحفاظ على قواعد العمل والبيانات الأساسية، وليس إعادة تشغيل ملفات Forms القديمة داخل التطبيق الجديد. سيكون مشروع Mido هو طبقة التطبيق المكتبي الحديثة، بينما يبقى Oracle على خادم Ubuntu طبقة البيانات المرحلية أو الإنتاجية بعد التحقق من المخطط والعلاقات.

## 2. مصادر التحليل المحفوظة

| المصدر | الحالة | الاستخدام |
|---|---|---|
| `ERP_DBA.fmx` | محلل نصياً | إدارة قاعدة البيانات، الشركة، الفروع، المستخدمون، السنوات، الإعدادات، ومصمم التقارير |
| `Lib.zip` | محلل دون تشغيل الثنائيات | المكتبات المشتركة، POS، طلبات الشراء، الموردون، الصلاحيات، والطباعة |
| `Forms.zip` | جرد وتحليل دفعي لـ 1,490 ملف FMX | خارطة واسعة للوحدات والشاشات وسير العمل والحقول |
| Oracle Data Pump inventory | موثق سابقاً | 923 جدولاً و200 View و13 Sequence حسب الجرد الموجود |
| مشروع Mido | أساس التنفيذ | تطبيق Electron عربي RTL مع مخطط أمان وسنوات مالية وواجهة أولية |

النسخ الأصلية محفوظة محلياً داخل `reference_archives/` مع بصمات SHA-256، بينما استُبعدت الأرشيفات الكبيرة من GitHub. لا يتم تشغيل ملفات DLL أو OCX أو EXE أو PLX أو FMX القديمة.

## 3. خريطة الوحدات المستنتجة

| المجال | مؤشرات Forms/Oracle | التصميم المستهدف في Mido |
|---|---|---|
| الأمن وتسجيل الدخول | `ERP_LOGIN`، `IAS_USR_LGN_HSTRY`، `PRIVILEGE`، `IAS_USER_GROUP`، `IAS_DATE_LOCK_USER` | مستخدمون وأدوار وصلاحيات ونطاق شركة/فرع/سنة وسجل تدقيق |
| المحاسبة العامة | `ACCOUNT`، `ACCOUNT_TYPES`، `MASTER_JOURNAL_V`، `DETAIL_JOURNAL_V`، `IAS_GL_*`، بادئات `GLSI/GLSR/GLST/GLSS` | دليل حسابات هرمي، قيود مزدوجة، مراكز تكلفة، أبعاد، فترات، ميزان مراجعة، قائمة دخل، وميزانية |
| العملاء والمبيعات | `CUSTOMER`، `SALES_ORDER`، `SALES_MAN`، `IAS_AR_*`، بادئات `ARSI/ARSR/ARST/ARSS` | العملاء، عروض وأوامر وفواتير ومرتجعات وتحصيلات وأعمار ذمم وعمولات |
| الموردون والمشتريات | `VENDOR`، `IAS_AP_*`، `IAS_PUR_PLAN_*`، `APSI/APSR/APST/APSS`، `APST015` | الموردون، طلبات الشراء، أوامر الشراء، الفواتير، المرتجعات، الدفعات والاستحقاقات |
| المخزون والمستودعات | `ITEM_MOVEMENT`، `WAREHOUSE_DETAILS`، `IAS_ITEM_*`، `IAS_BATCH_NO`، `INVI/INVS/INVT/INVR` | الأصناف، الوحدات، المستودعات، التحويلات، الجرد، التكلفة، الدفعات، التسلسل وحد إعادة الطلب |
| نقاط البيع | `YSPOS_MNU.mmx`، `IAS_POS_BILL_MST/DTL`، `POSI/POSR/POSS` | POS مستقل مع النقد والبطاقات والشيكات والمرتجعات وربط القيود |
| التصنيع والتخطيط | `MRP*`، `BOM`، `MPS`، `WORK`، `QUALITY` | مرحلة لاحقة تشمل BOM، أوامر التصنيع، التخطيط، الجودة ومراكز العمل |
| الموارد البشرية | `HRS*` و`HRSS031.fmx` و`HRST*` | مرحلة لاحقة منفصلة عن النواة المحاسبية، مع الرواتب والحضور والإجازات |
| الأصول والصيانة والمشاريع | `FAS*`، `MNT*`، `PMS*`، `PROJECT` | أصول ثابتة، صيانة، مشاريع ومراكز تكلفة بعد تثبيت المحاسبة الأساسية |
| التقارير والطباعة | ملفات `ARSR/GLSR/INVR/...` وملفات RDF | محرك تقارير حديث يخرج PDF/XLSX مع قوالب عربية، دون الاعتماد على Oracle Reports Runtime |

## 4. تصميم طبقات النظام

تتكون النسخة المستهدفة من تطبيق Electron بواجهة RTL، وطبقة خدمات داخلية، وطبقة مستودع بيانات، وطبقة تكامل Oracle. في وضع الترحيل الأول يمكن استخدام Oracle بحساب تطبيق منفصل للقراءة والعمليات المصرح بها، مع منع استخدام `SYSTEM`. يجب أن تكون كل عملية ترحيل محاسبي مرتبطة بالشركة والفرع والسنة والفترة والصلاحية والتاريخ المحاسبي.

يجب أن يكون لكل مستند دورة واضحة: مسودة، مراجعة، اعتماد، ترحيل، إلغاء أو عكس. لا تُعدّل القيود المرحلة مباشرة؛ بل تُنشأ قيود عكسية أو تسويات مع سجل تدقيق. وتُفصل بيانات الإعدادات عن بيانات العمليات وعن جداول التدقيق.

## 5. ترتيب التنفيذ المقترح

| المرحلة | الناتج |
|---|---|
| A | اتصال آمن بخادم Oracle وقراءة Metadata من Schema مرحلي |
| B | شاشة الدخول، الشركة، الفرع، السنة، الصلاحيات وسجل التدقيق |
| C | دليل الحسابات والقيود والفترات والتقارير المالية الأساسية |
| D | العملاء والمبيعات والتحصيلات، ثم الموردون والمشتريات والمدفوعات |
| E | الأصناف والمستودعات وحركات المخزون والتكلفة والجرد |
| F | التقارير، التصدير، النسخ الاحتياطي، وإدارة الصلاحيات المتقدمة |
| G | POS، التصنيع، الموارد البشرية، الأصول، الصيانة والمشاريع |

## 6. متطلبات الاتصال بالخادم

لا يمكن اختبار خادم Ubuntu من مساحة العمل الحالية دون بيانات اتصال صريحة أو قناة وصول مفعلة. المطلوب من مسؤول الخادم هو: عنوان المضيف أو اسم DNS، منفذ SSH، اسم مستخدم SSH، طريقة المصادقة، عنوان Oracle Listener، المنفذ، اسم الخدمة أو الـ PDB، واسم Schema مرحلي للقراءة. لا تُرسل كلمات المرور داخل المحادثة أو المستودع؛ تستخدم متغيرات بيئة أو مدير أسرار.

يجب أولاً تنفيذ فحص غير تغييري: حالة Docker/Oracle، `lsnrctl status` أو حالة الحاوية، اختبار المنفذ، إصدار Oracle، اسم الخدمة، وقائمة المستخدمين والجداول. بعد ذلك يُستخرج DDL إلى ملف للمراجعة قبل أي Import. لا يُنفذ الاستيراد في الإنتاج، ولا يُمنح حساب التطبيق صلاحية DBA.

## 7. قرارات أمنية إلزامية

تحتوي بعض ملفات Forms القديمة على مؤشرات لبيانات اتصال أو كلمات مرور مضمنة. تعتبر هذه البيانات مكشوفة ويجب تدويرها فوراً وعدم استخدامها في النظام الجديد. كما يجب عدم تضمين DLL/OCX/EXE قديمة في حزمة التطبيق قبل مراجعة المصدر والتوقيع والترخيص؛ البديل هو إعادة تنفيذ الوظائف المطلوبة في JavaScript/TypeScript أو خدمة خادمية معزولة.

## 8. الحالة الحالية

تم تحديث مشروع Mido بواجهة أولية تفاعلية للوحدات الأساسية، وحفظ التحليلات والجرد في مجلد `oracle/`. كما رُفعت التعديلات إلى GitHub. ما ينقص للانتقال من التحليل إلى الربط الحقيقي هو الوصول إلى خادم Oracle ومراجعة Metadata والعلاقات الفعلية، ثم اختيار ما إذا كان Oracle سيبقى قاعدة التشغيل الأساسية أو سيكون مصدر ترحيل إلى SQLite/PostgreSQL.
